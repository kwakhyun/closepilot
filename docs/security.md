# 공개 데모의 보안 모델

지원서 검토자가 가상 거래로 전체 작업 과정을 체험하는 공개 데모다. 실제 고객 자료를 처리하는 운영 시스템으로 사용해서는 안 된다.

| 위협                           | 구현한 통제                                                                                                                     | 남는 한계                                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 다른 방문자의 자료 조회·수정   | 32바이트 난수 세션 토큰과 HttpOnly 쿠키 사용, DB에는 토큰의 SHA-256 해시만 저장, 세션별 조회 조건 적용                          | 사용자 계정·조직별 권한 관리 기능은 아니다. 토큰이 탈취되면 해당 세션에 접근할 수 있다.                     |
| 다른 사이트에서 보낸 변경 요청 | SameSite=Lax, POST의 Origin·Host·Sec-Fetch-Site 검사                                                                            | 브라우저 외부에서 세션을 만드는 클라이언트의 신원을 인증하지는 않는다.                                      |

## 데이터 수명

세션을 생성한 뒤 6시간이 지나면 API 접근이 차단된다. 다음 세션을 생성하는 트랜잭션에서 만료된 작업 데이터와 해당 요청 처리 이력·감사 기록을 삭제한다. 이후 접속이 없으면 데이터가 DB에 더 오래 남을 수 있다. **새 데모 시작**은 새 세션을 만들며 이전 데이터를 즉시 삭제하지는 않는다. 정해진 시각의 삭제 보장, 변경 불가능한 장기 보관(WORM), 법정 보존 의무를 충족하는 보관 정책은 구현·검증하지 않았다.

연결하지 않은 CSV 열은 저장하지 않는다. 원본 파일 자체를 보관하는 대신 표준 필드와 내용 체크섬(`digest`)을 저장한다. 주문번호나 메모에도 개인정보가 들어갈 수 있으므로 **개인정보를 자동으로 제거하는 기능은 제공하지 않는다.**

## 응답과 플랫폼 경계

작업 상태 API에는 `Cache-Control: no-store, private`를 적용한다. 공개 배포의 쿠키에는 `Secure`, `HttpOnly`, `SameSite=Lax`를 설정한다. CSP, 외부 프레임 삽입 차단, `nosniff`, Referrer-Policy, Permissions-Policy도 적용한다. 현재 CSP는 Next.js의 초기 실행 스크립트를 위해 `unsafe-inline`을 허용하며 nonce 방식까지 적용하지는 않았다. 프로덕션에서는 `unsafe-eval`을 허용하지 않는다.

DB 연결 문자열과 Vercel 토큰은 로컬 환경 설정 또는 플랫폼의 비밀값 저장소에서 관리하고 Git에 포함하지 않는다. `.env.example`에는 비밀값이 없다. CI의 DB URL에는 임시 테스트 DB용 비밀번호만 포함하며 운영 DB 비밀번호는 사용하지 않는다.

## 실사용 전 필수 조건

실제 고객과 법무·보안 담당자에게 데이터 처리·보관 정책을 확인해야 한다. 기업 로그인(SSO), 역할별 권한(RBAC), 조직별 데이터 분리, 작성자·승인자 분리, 원본 자료의 서명·보관, 감사 권한 분리도 필요하다. WAF, 작업 큐, 모니터링, 복구 시험을 포함한 운영 체계를 별도로 마련해야 하며, 실제 결제·회계 판단은 담당자와 원천 시스템의 검증을 거쳐야 한다.
