# 제품 기획: 근거를 남기는 매출 마감

## 출발점과 가설

이 프로젝트는 B2B 커머스 운영에서 고객 업무를 이해하고 문제를 정의한 뒤, 구현과 배포를 거쳐 재사용 가능한 기능으로 만드는 과정을 가상 시나리오로 구현한다. 실제 고객 인터뷰는 진행하지 않았다. 아래의 브랜드와 담당자, 업무상 어려움은 제품 설계를 위한 가정이다.

가상 K-Beauty 브랜드 LUMIÈRE와 K-Food 브랜드 MORROW FOODS의 재무 담당자는 월말에 서로 다른 판매 채널 자료를 받아 주문별 정산액을 비교한다. 브랜드마다 열 이름과 계약 요율이 다르고, 차이의 원인을 별도 문서에 기록하면 다음 검토자가 금액과 설명을 다시 대조해야 한다고 가정했다.

**핵심 질문:** 어떤 거래에 차이가 있고, 어떤 근거로 검토했는가?

## 범위 결정

| 우선순위 | 사용자 작업         | 완료 기준                                                                                  |
| -------- | ------------------- | ------------------------------------------------------------------------------------------ |
| P0       | CSV 자료 가져오기   | 열을 연결하고 반영 전에 오류를 확인한다. 오류가 있으면 파일 전체를 반영하지 않는다.        |
| P0       | 주문·정산 비교      | 같은 입력에서 동일한 원 단위 금액과 예외 분류를 재현한다.                                  |
| P0       | 차이 검토           | 검토 사유와 증빙 참조 정보가 있어야 승인할 수 있다. 승인 후에도 원본 차액을 유지한다.      |
| P0       | 마감 확정           | 최신 자료 대사와 모든 예외 거래 검토를 마쳐야 확정할 수 있다. 확정 후에는 변경을 차단한다. |
| P0       | 인수인계            | 입력·규칙 버전·결과·검토 근거·감사 기록을 한 파일로 내보내고 Kotlin으로 재검증한다.        |
| P1       | 검토 순서 결정      | 차액 정렬, 채널·상태 필터, 원본 자료에 근거한 검토 가이드를 제공한다.                      |
| P1       | 온보딩 자산화       | 채널·요율·열 연결·검토 규칙을 버전형 프로필로 저장하고 새 브랜드 설정으로 복제한다.        |
| P1       | 진단과 로드맵 연결  | 문제 가설·확인 질문·적용 설정·공통 기능·관찰 지표를 한 화면에서 추적한다.                  |
| P1       | Kotlin 대사 경계    | 프로필 요율과 주문·정산 입력을 받는 `/reconcile` REST 계약으로 핵심 계산을 실행한다.       |
| 제외     | 실제 결제·회계 처리 | 결제·환불·송금·분개·세금 신고를 수행하지 않는다.                                           |

이 데모의 “마감”은 **검토 결과와 근거를 담은 증빙 파일의 확정**을 뜻한다. 실제 월 재무제표를 확정하거나 PG 지급을 승인하는 기능이 아니다. 누락·중복 거래도 사유를 남겨 검토를 승인할 수 있지만, 원본 금액이나 회계 장부를 수정하지는 않는다.

## 현장 인터뷰에서 확인할 질문

1. 마감 완료의 정의와 최종 승인자는 누구인가? 마감 후 수정은 어떤 결재 절차를 거치는가?
2. 거래 ID는 채널/상점/주문/상품 단위 중 어디에서 유일한가? 분할 정산은 어떻게 식별하는가?
3. 환불 시 수수료는 언제, 어떤 기준으로 돌려받는가? VAT·프로모션·배송비는 어느 금액에 포함되는가?
4. 실제 입금 여부를 최종 확인할 때 정산 파일과 은행 거래 내역 중 어떤 자료를 기준으로 삼는가? 휴일이나 월이 바뀌는 시점은 어떻게 처리하는가?
5. 어떤 예외 거래를 다음 달로 이월할 수 있는가? 허용 오차와 증빙 보관 기간은 어떻게 정하는가?
6. 원본 자료의 개인정보, 접근 권한, 국외 처리, 보관·삭제 정책은 무엇인가?

## 온보딩 체크리스트

실제 도입 시에는 계약 수수료율, 반올림 방식, 매출 인식일을 먼저 문서로 합의한다. 거래 ID와 판매 채널의 대응 관계를 확인하고 정상 거래, 부분 환불, 중복, 누락, 다음 달 입금 사례를 각각 받는다. 과거 한 달의 자료를 기존 방식과 나란히 대사해 수기 결과와 비교한다. 승인자를 지정하고 오류나 장애가 발생했을 때 복구하는 절차를 확인한 뒤 적용 범위를 넓힌다.

LUMIÈRE의 3.3%, 3.85%, 8.8%와 MORROW FOODS의 2.9%, 7.2%는 모두 데모용 가정이며 실제 채널 요율이 아니다. 원화(KRW)와 2026년 8월 마감만 지원한다. 프로필을 바꾸거나 복제하면 기존 승인 결과를 다시 쓰지 않고 별도의 6시간 데모 세션을 만든다.

## 측정 계획: 아직 측정하지 않은 운영 성과

| 지표                  | 정의                                                           | 측정 계획                                                 |
| --------------------- | -------------------------------------------------------------- | --------------------------------------------------------- |
| 온보딩 소요 시간      | 입력 규칙 합의부터 첫 대사 완료까지 걸린 시간                  | 고객별 작업 이력과 단계별 지연 원인 기록                  |
| 검토 소요 시간        | 파일 확보 후 최종 승인까지 담당자가 실제 작업한 시간           | 같은 달 자료로 기존 방식과 비교하고 대기 시간은 별도 집계 |
| 검토 근거 기록률      | 증빙 참조 정보와 검토 사유를 갖춘 예외 거래 / 전체 예외 거래   | 입력 내용과 표본 증빙 확인                                |
| 잘못된 일치 판정 비율 | 자동 일치 거래 중 외부 자료와 비교했을 때 불일치한 거래의 비율 | 은행·PG 원본과 표본 대조                                  |
| 결과 재현성           | 같은 입력·규칙 버전에서 동일한 결과가 나오는지 여부            | 고정 검증 데이터와 Kotlin 재계산                          |

LUMIÈRE 128건과 MORROW FOODS 96건의 샘플은 프로필별 계산 결과와 예외 8건이 변경 후에도 유지되는지 확인하기 위한 자료다. 제품·시장 적합성(PMF), 업무 시간 절감, 실제 고객 자료의 대사 정확도를 입증하는 수치는 아니다.

## 제품화할 자산과 다음 결정

채널별 차이는 CSV 열 연결과 계약 정책을 담은 버전형 온보딩 프로필로 분리하고, 금액 계산·대사·검토 승인 규칙은 공통 기능으로 유지한다. CSV 반영과 열 연결 저장은 같은 트랜잭션에서 처리하며, 프로필 스냅샷은 마감 패키지에도 포함한다. Kotlin `/reconcile`은 같은 프로필 요율로 핵심 계산을 독립적으로 실행해 계약 일치 여부를 검증한다.

다음 단계에서는 실제 고객 자료를 사용하기 전에 거래 ID 유일성, 요율 유효기간, 분할 정산, 원본 자료 버전과 결재 절차를 인터뷰로 확인한다. 관찰할 지표는 첫 열 연결 완료율, 자동 연결률, 정책 변경 후 재검토 누락, 근거 요청 왕복 횟수다. 현재 화면의 진단 결과와 지표는 이 검증 방법을 설명하기 위한 가상 예시이며 측정된 성과가 아니다.
