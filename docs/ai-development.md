# AI를 포함한 개발 절차

이 프로젝트는 Codex와 함께 제품 범위, 도메인 코드, UI, 테스트, 배포 설정, 문서를 작성했다. AI가 작성한 코드를 검증하지 않은 채 “정확하다”고 주장하지 않기 위해 다음 작업 계약을 저장소에 남겼다.

## 실제 사용하는 자산

| 자산                             | 역할                                                              |
| -------------------------------- | ----------------------------------------------------------------- |
| `AGENTS.md`                      | 도메인·보안·정직한 주장·검증 순서의 공통 계약                     |
| `CLAUDE.md`                      | 동일한 계약을 참조해 에이전트별 지침 중복을 줄임                  |
| `scripts/check-architecture.mjs` | TypeScript AST에서 import 경계와 클라이언트의 서버 의존성 검사    |
| `.githooks/pre-commit`           | 커밋 전 레이어·타입·도메인/DB 테스트 실행                         |
| `.github/workflows/verify.yml`   | PR/push에서 빌드, PostgreSQL 테스트, 실제 API 흐름, Kotlin 재계산 |
| `fixtures/closed-package.json`   | 고정 입력·고정 시각으로 재생성 가능한 검증 계약                   |

훅 활성화: `git config core.hooksPath .githooks`. 훅은 우회 가능하므로 CI 결과와 사람이 확인한 근거를 함께 본다.

## 구체적인 변경 예: 수수료 정책

먼저 어떤 계약이 바뀌었는지 확인한다. 다음에 반올림 경계값과 부분 환불을 포함한 반례를 작성한다. TypeScript와 Kotlin을 각각 수정하고 규칙 버전을 올린다. 픽스처를 재생성한 뒤 행별 차이가 의도한 변경인지 확인한다. UI에 남아 있는 요율 설명과 운영 문서도 같은 기준으로 갱신한다.

계약 근거 없이 숫자를 바꾸거나, 검증 결과를 맞추려고 예상값만 바꾸는 작업은 허용하지 않는다. 생성된 결과가 맞다는 근거는 AI의 답변이 아니라 테스트 입력·불변식·독립 재계산이다.

## 구현 중 발견하고 수정한 문제

- 로컬 PGlite의 부모 디렉터리가 없으면 DB 초기화가 실패했다. 부모 디렉터리를 명시적으로 생성했다.
- Next의 내부 URL과 브라우저의 public Host가 달라 정상 POST가 Origin 검사에서 거부됐다. Host/명시적 APP_ORIGIN 경계를 정리하고 HTTP 회귀 테스트를 추가했다.
- 500 오류 body와 header의 requestId가 달라 로그를 연결하기 어려웠다. 같은 ID를 body/header/log에 사용하도록 수정하고 비밀 정보 비노출을 테스트했다.
- Windows의 한글 경로에서 Kotlin 테스트 classpath가 깨졌다. CLI 스크립트에서 빌드 출력만 ASCII 임시 경로로 분리했다. 동일한 테스트와 재계산을 다시 실행했다.

## 제품의 AI 기능과 구분

공개 PostgreSQL 검증에서는 JSON 문자열을 드라이버가 다시 직렬화하는 차이가 발견됐다. PGlite가 이미 직렬화된 문자열도 허용해 로컬 테스트만으로 드러나지 않은 문제였다. 네이티브 객체를 드라이버에 전달하도록 수정하고, JSON 객체 여부와 필수 필드를 DB 제약으로 확인하게 했다. 신규 쓰기에 적용하는 추가 마이그레이션과 두 개의 회귀 테스트를 추가한 뒤 공개 API 20단계를 다시 통과했다.

첫 Vercel 배포에서는 Next 16.3의 standalone/adapter 조합이 trace 파일을 찾지 못했다. 로컬 빌드만 통과한 상태에서 성공으로 처리하지 않고, 패키지 코드와 [동일한 재현 이슈](https://github.com/vercel/next.js/issues/96646)를 확인해 배포 대상에 따라 output 설정을 분리했다.

공개 앱은 LLM API를 호출하지 않는다. 검토 가이드는 규칙 엔진이 반환한 행·설명·source ID를 표시한다. 채팅, Agent SDK, LangGraph 또는 실사용 LLM 에이전트를 구현했다는 주장을 하지 않는다.

추가한다면 다음 경계를 유지한다: 제한된 증빙 ID만 읽는 설명 API, JSON 스키마, 원본 참조 검증, 시간/비용 한도, 개인정보 최소화, 실패 시 결정적 가이드. 금액 계산·원본 수정·승인·마감·송금 도구는 설명 에이전트에 제공하지 않는다. API 키·예산·데이터 처리 정책의 합의와 별도 평가가 선행되어야 한다. 이는 **설계 제안이며 현재 기능이 아니다.**
